# Terraform provider 0.3.0 — design spec

Date: 2026-09-09  
Status: **implemented** (homelab E2E: offering/tenant/volume/full-stack pass; VM in-place resize apply blocked until core stop fix is deployed)  
Repos: `virtfoundry/terraform-provider-virtfoundry` (code), `virtfoundry/core` (mapping table in `docs/TERRAFORM-PROVIDER-PLAN.md`)  
Min API: VirtFoundry **>= 0.5.0** (volume delete, offerings CRUD, `dedicated_cpu`, tenant delete)

Catch the provider up to REST features that already work in homelab. Load balancer stays out.

---

## 1. Goal

Ship **terraform-provider-virtfoundry 0.3.0** so Terraform can:

- Delete volumes (PVC) and tenants the way the API does today
- Attach and detach data volumes after deploy
- Manage the service-offering catalog (root) including `dedicated_cpu`
- Deploy VMs with `dedicated_cpu` and resize via `PATCH` (`service_offering_id`) without recreate

**Success:** new/updated resources apply and destroy against `http://virtfoundry.homelab`; `scripts/test-*.sh` pass; changelog and docs say `0.3.0`; no GitHub release until those E2E runs are green.

## 2. Non-goals

- Load balancer, target group, listener, or target resources (dataplane not reliable yet).
- Volume snapshot delete (API still has no `DELETE /snapshots/{id}`).
- Terraform Registry publish / git tag — happens after E2E, as a separate step.
- Changing VirtFoundry core API or UI.
- Playwright or browser tests.
- Replacing `data_volume_id` on `virtfoundry_vm` (deploy-time attach stays).

## 3. Locked decisions

| Topic | Decision |
|-------|----------|
| Version | `0.3.0` (minor + breaking volume destroy) |
| Volume attach | New resource `virtfoundry_volume_attachment` (AWS-style), not `vm_id` on the volume |
| Deploy-time disk | Keep `virtfoundry_vm.data_volume_id`; do not attach the same volume via both fields |
| Offerings | New resource `virtfoundry_service_offering` (root). Data source stays and gains `dedicated_cpu` |
| Offering destroy | `DELETE /service-offerings/{id}` (API hard-deletes; Read treats missing as gone) |
| VM resize | Remove `RequiresReplace` on `service_offering_id`; Update sends `PATCH` with that field |
| VM `dedicated_cpu` | Optional bool, `RequiresReplace` (API `PATCH /vms/{name}` does not accept it) |
| Volume destroy | Call `DELETE /volumes/{id}`. 409 if attached → Terraform error, not orphan |
| Tenant destroy | Call `DELETE /tenants/{id}`. API forbids slug `default` |
| Snapshot destroy | Unchanged: clear state only, warning |
| E2E home | Provider `scripts/test-*.sh` against homelab, same pattern as `test-vm.sh` / `test-full-stack.sh` |
| Release | No tag/Registry in this slice |

## 4. Architecture

Unchanged: Terraform CLI → plugin-framework provider → REST `/api/v1` (JWT or API key + `X-Tenant-ID`). No KubeVirt calls from the provider.

```
terraform apply
    → virtfoundry_* resources
        → Client JSON methods
            → VirtFoundry API
```

New client methods live in `internal/virtfoundry/` next to the existing volume/VM/tenant helpers. Resources live in `internal/provider/` and register in `provider.go`.

## 5. Resources

### 5.1 `virtfoundry_volume` (change)

`Delete` calls `DELETE /api/v1/volumes/{id}`. Success removes PVC and store record.

If the API returns 409 (volume attached), surface the error. Operator must destroy `virtfoundry_volume_attachment` first (Terraform graph does this when both are in the same config).

`vm_id` stays **computed** from `GET` list/get volume.

Docs: destroy now deletes the volume. This is a **breaking** change vs 0.2.0 (destroy previously only cleared state).

### 5.2 `virtfoundry_volume_attachment` (new)

Maps to hot-plug attach/detach.

```hcl
resource "virtfoundry_volume_attachment" "data" {
  tenant_id = optional(string) # default: provider tenant_id
  vm_name   = virtfoundry_vm.app.name
  volume_id = virtfoundry_volume.data.id
}
```

| Attribute | Role |
|-----------|------|
| `id` | Computed; equals `volume_id` (a volume attaches to at most one VM) |
| `tenant_id` | Optional, `RequiresReplace` |
| `vm_name` | Required, `RequiresReplace` |
| `volume_id` | Required, `RequiresReplace` |

- **Create:** `POST /api/v1/vms/{vm_name}/volumes` body `{"volume_id":"..."}` (HTTP 200).
- **Read:** `GetVolume`; if not found or `vm_id` empty, remove from state (detached outside Terraform).
- **Update:** none (all force-new).
- **Delete:** `DELETE /api/v1/vms/{vm_name}/volumes/{volume_id}`.
- **Import:** `tenant_id/volume_id` or `volume_id` when provider `tenant_id` is set.

Do not send `data_volume_id` on the VM and also attach that same volume here. API returns “volume already attached”.

### 5.3 `virtfoundry_service_offering` (new, root)

```hcl
resource "virtfoundry_service_offering" "xl" {
  name          = "e2e-xl"
  display_name  = "E2E XL"
  cpu           = 2
  memory_mi     = 2048
  dedicated_cpu = false
}
```

| Attribute | Role |
|-----------|------|
| `id` | Computed |
| `name` | Required, `RequiresReplace` (API create slug; PATCH cannot rename) |
| `display_name` | Optional; defaults to name on create |
| `cpu` | Required int > 0; updatable |
| `memory_mi` | Required int > 0; updatable |
| `dedicated_cpu` | Optional bool, default false; updatable |
| `state` | Computed (`Active` after create) |

- **Create:** `POST /api/v1/service-offerings` (root). HTTP 201.
- **Read:** `GET /service-offerings` (active list is enough; destroy hard-deletes). Match by id. Missing → remove from state.
- **Update:** `PATCH /api/v1/service-offerings/{id}` for `display_name`, `cpu`, `memory_mi`, `dedicated_cpu`. Changing catalog size does **not** resize existing VMs.
- **Delete:** `DELETE /api/v1/service-offerings/{id}`.
- **Import:** offering id.

Requires root credentials (`requireRootClient`), same as `virtfoundry_tenant`.

### 5.4 `data.virtfoundry_service_offerings` (change)

Each nested offering gains computed `dedicated_cpu` (bool). Existing fields unchanged.

### 5.5 `virtfoundry_tenant` (change)

`Delete` calls `DELETE /api/v1/tenants/{id}`.

API returns forbidden for the default tenant. Terraform shows that error; do not swallow it.

This is not a silent behavior change for working destroy: 0.2.0 already **errored** on tenant destroy. 0.3.0 makes destroy succeed for non-default tenants.

### 5.6 `virtfoundry_vm` (change)

Add optional `dedicated_cpu` (bool). `RequiresReplace`. Send as `dedicated_cpu` on `POST /vms`. After read, store the API value (offering with `dedicated_cpu` forces the VM dedicated even if the attribute was omitted).

Remove `RequiresReplace` from `service_offering_id`. On Update, if it changed, `PATCH /vms/{name}` with `{"service_offering_id":"..."}`. Do not also send `cpu` / `memory_mi` in that request; the API copies them from the offering.

`data_volume_id` unchanged (deploy-time attach, still `RequiresReplace`).

Extend client `VM` with `DedicatedCPU bool` and `UpdateVM` to accept `service_offering_id` (prefer a small `UpdateVMInput` struct over more positional args).

### 5.7 `virtfoundry_volume_snapshot`

No change. Destroy still warns and clears state only.

## 6. Client API additions

All in `internal/virtfoundry/`:

| Method | HTTP |
|--------|------|
| `DeleteVolume(ctx, tenantID, id)` | `DELETE /volumes/{id}` |
| `AttachVolume(ctx, tenantID, vmName, volumeID)` | `POST /vms/{vmName}/volumes` |
| `DetachVolume(ctx, tenantID, vmName, volumeID)` | `DELETE /vms/{vmName}/volumes/{volumeID}` |
| `DeleteTenant(ctx, id)` | `DELETE /tenants/{id}` (no tenant header) |
| `CreateServiceOffering` / `UpdateServiceOffering` / `DeleteServiceOffering` / `GetServiceOffering` | root `/service-offerings` |
| `UpdateVM` | `PATCH` body may include `service_offering_id` |
| `DeployVMInput.DedicatedCPU` | `dedicated_cpu` on create |

Remove `ErrDeleteNotSupported` usage from volume (and tenant). Volume snapshot may still warn without that sentinel.

409 / 403 / 404 map through existing `apiError`; resources interpret 404 as gone on Read.

## 7. Error handling

| Case | Behavior |
|------|----------|
| Delete volume while attached | Error with API message; state kept |
| Attach already-attached volume | Error; do not mark created |
| Detach missing volume / already detached | Delete is idempotent: 404 → success (clear state) |
| Delete default tenant | Error; state kept |
| Delete missing tenant/volume/offering | Delete success (idempotent) |
| Resize to unknown offering | Error; state kept |

## 8. Testing

Unit (`go test ./...`): httptest fixtures for delete volume, attach/detach, offering CRUD, tenant delete, VM PATCH with `service_offering_id` and deploy with `dedicated_cpu`.

E2E (homelab, `VIRTFOUNDRY_ENDPOINT` default `http://virtfoundry.homelab`, `root` / `virtfoundry`):

| Script | Asserts |
|--------|---------|
| `scripts/test-volume.sh` | Apply a Cirros VM + volume + attachment in one example; `plan` exit 0; destroy (attachment then volume); `GET /volumes` no longer contains the id |
| `scripts/test-offering.sh` | Root apply offering with `dedicated_cpu=true`; data source lists it; destroy; offering gone from `GET /service-offerings` |
| `scripts/test-tenant.sh` | Apply throwaway tenant (unique slug); destroy; tenant absent from `GET /tenants` |
| `scripts/test-vm.sh` | VM with `dedicated_cpu=false` on seeded `small`; second apply sets `service_offering_id` to seeded `medium`; `terraform plan -detailed-exitcode` after first apply is 0; second apply must not replace the VM (`-replace` absent); destroy |
| `scripts/test-full-stack.sh` | Add volume + attachment to the stack; keep existing VPC/net/SG/SSH/VM checks |

Examples for the new scripts live under `examples/volume/`, `examples/offering/`, `examples/tenant/` (minimal HCL, unique names via `-var` like today).

No core `scripts/e2e/` changes unless a REST bug is found; then fix core in a separate PR.
